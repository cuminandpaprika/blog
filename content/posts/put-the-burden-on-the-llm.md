# Attention is all you need

The tech industry has finally realised the importance of attention. [Attention Is All You Need](https://arxiv.org/abs/1706.03762) might actually be the most cited paper in computer science in recent years. However all the *ahem* attention is on the wrong kind of [attention](https://en.wikipedia.org/wiki/Attention_(machine_learning)). Human attention is now more valuable than ever. Of course, social media companies such as Facebook and MySpace knew this since the early 2000s, and advertising giants such as Google realised this in a similar time frame. Now it's time for every other industry to understand the value of human attention. It seems like everyone is grappling with the following problem: 

> How do we preserve the finite human attention in a sea of noise generated by AI Agents?

# Prompting

A common way that beginners use LLMs when instructing them to complete a task is to spend 20 minutes writing an essay describing what needs to be done. This is usually after they realised that a one sentence prompt or an insufficient prompt produced absolute garbage. When you explicitly tell the LLM what to do, it's great at following instructions. When you don't give it the details, it assumes and makes decisions on your behalf. If you're vibe-coding a proof-of-concept, that's completely fine. When you want to ship code to prod, that's a big problem.

But there are a few ways that we can improve upon essay-prompting:

- First of all, when we write huge prompts, we don't know what the LLM can figure out on its own.
- Second of all, we don't know what we forgot to mention in our essay, so whatever doesn't make it in the initial prompt will likely be assumed and decided on by the LLM.
- Finally, we have to think hard and use more brain power to extract the information needed for the prompt.

What if we flip the burden and make the LLM ask us for all the questions it needs? Matt Pocock's [grill-me](https://github.com/mattpocock/skills/blob/main/skills/productivity/grilling/SKILL.md) skill is an excellent example of how this works in practice. If we tell the LLM to first try and see what information it can find out itself, that vastly reduces the amount of input we need to provide.

Here's an example of an exploratory prompt where we send the agent to figure out what it can and present us a list of questions, one at a time:

```
I want to add an in-memory cache to the foo service for the /bar API call. Check the code then /grill-me
```

It then comes back and asks you questions to clarify the design, one at a time. Now all we need to do is select from multi-choice answers and type short sentences to express our intent. This saves time and also preserves our attention for the most valuable activity that humans do these days: decision making.

# First Review

Let's assume that the LLM came back with a finished implementation of your feature. How do we understand what it did and review its work? We have a few options, we can either:

A. Review the code
B. Test the implementation ourselves
C. Ask the LLM to test it
D. Close our eyes and ship it to prod

Probably options A and C are the most reasonable. We want to look at the code if we care about it. We also want to verify it works, but we can use a new agent with clean context to do that. Simon Willison writes about [Agentic Manual Testing](https://simonwillison.net/guides/agentic-engineering-patterns/agentic-manual-testing/) in great detail; it works especially well for frontend testing with Playwright or the Claude Code Chrome plugin.

# PR Review

Okay now we're reasonably confident that the code matches our intent, it works and we're ready to get our feature merged. In the vast majority of workplaces, we still operate with the norms of pre-AI: Agentic coding tools use a human's git credentials. Code must be reviewed by another human before merge. So how do we make this process easier for our teammates?

Personally, I've found great success with using an extremely detailed and laborious PR template. In pre-AI days, we never would've expected anyone to reasonably write up their pull request like a PhD thesis. But now that tokens are cheap and human attention is expensive, we want to reduce human effort and attention burden during the PR review as much as possible.

So we ask the LLM to justify to a reviewer why this change is necessary, what were the decisions, what are the risks introduced by this change. By surfacing this information, the goal is to lift out the important information relating to a change and make it easy for a reviewer to see it at a glance.

Here's the general structure of a PR template that's been working well for my team:

```
# Why

Why is this change necessary?

Ticket: XXX-1234
Risk: Low/Medium/High

# What

> Toggle List of changes, so we present information with correct levels of descending abstraction.

# Decisions

- A list of decisions made during the implementation of this change

# Risks and things to scrutinise

- List out all the high risk areas or controversial decisions.

```

# Conclusion

We're really only scratching the surface of the types of use-cases that LLMs are well suited for. We need to keep in mind the theory of constraints: if we automate and increase the throughput of one part of the system, we need to do the same thing downstream. Humans don't scale like LLMs do; if a human needs to keep up with machines, that's a recipe for disaster. This philosophy doesn't just apply to coding agents — when we bake LLMs into any product, we want to ensure that we fully automate a process end-to-end. If an AI Agent performs a task on a user's behalf, it should also verify the work and present this in an easy-to-digest, easy-to-review format.
